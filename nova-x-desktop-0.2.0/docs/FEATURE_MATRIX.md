# NOVA X feature status — multi-model and bounded autonomy foundation

“Implemented” describes code in this repository, not a provider entitlement or live deployment. Automated provider tests use fake HTTP/model responses. No live provider credentials were used during this implementation.

| Area | Status | What exists / limitation |
|---|---|---|
| Existing browser command center | Implemented; JS syntax checked; full device/browser review recommended | Separate legacy FastAPI/static interface with chat/task/model views. It is not the native Kali desktop deliverable and is not opened by the desktop launcher. |
| Native Kali/Linux desktop | Implemented as first increment; Python/tests/package/CLI checked; GUI/Kali install untested | PySide6/Qt shell, local runtime, SQLite tasks/history, task plan/approval/control UI, direct local process runner, workspaces, permissions, model profiles, keyring, diagnostics, CLI, desktop entry, `.deb`. The sandbox has no Qt/display/keyring/polkit, so the window and target-machine installation remain unvalidated. See `docs/NATIVE_DESKTOP.md`. |
| Local process execution | Implemented in native app; unit/task/CLI tests pass; host compatibility untested | Structured argv subprocess execution, real result/exit code, timeout, process-group stop, bounded stdout/stderr, private logs, default user privileges, exact-prefix approval policy. Model tool calls cannot pass shell strings or invoke shells, interpreters/build runners, file scanners, or indirect command wrappers. User-authored Bash is a separate fresh-confirmation mode. |
| Native credential storage | Implemented; fake Secret Service tests; no live desktop keyring available | Linux Secret Service backend only; unmanaged provider-key environment values are ignored; key values are not stored in SQLite/logs/source/child process environment. Live unlock/prompt behavior remains untested. |
| Native installer/desktop integration | `.deb` built and inspected; not installed | `releases/nova-x-desktop_0.2.0_all.deb`, CLI wrapper, `.desktop` entry, scalable SVG icon, Debian dependencies. Package extraction and non-GUI CLI smoke tested; actual `apt install` on Kali not performed. |
| Multi-provider registry | Implemented; deterministic API tests | OpenAI, OpenAI-compatible, Anthropic, Gemini, xAI, DeepSeek, Mistral profile types. Profiles store server credential references, endpoint, model ID, declared chat/tool capabilities, priority/rates, enable/default controls, and status metrics. No raw key is returned/accepted. Deleting/disabling a profile does not revoke the provider key; revoke it separately in the provider account/host secret manager. |
| Live model catalogs | Implemented; adapters mocked; live account access untested | OpenAI-compatible `/models`, Anthropic `/v1/models`, Gemini paginated model list. Completeness is surfaced; incomplete catalog does not falsely mark an ID absent. Catalog listing does not prove account entitlement/tool support; identifier-only catalogs do not prove chat capability and require a successful inference test before routing. |
| Native API behavior | Partially implemented; request/normalization tests | Anthropic native Messages and Gemini native `generateContent`; OpenAI uses `max_completion_tokens`. xAI/DeepSeek/Mistral use compatible Chat Completions. xAI adapter is on a legacy/deprecated surface; Responses API migration not implemented. |
| Credential security | Implemented; automated validation tests | Web/server profiles use provider-specific server environment references. Native profiles use Linux Secret Service only and ignore unmanaged provider-key environment variables. Provider host allowlist, HTTPS default, disabled redirects, strict API schemas. Custom endpoint requires explicit config **and** access-token auth. |
| Provider connectivity/inference test | Implemented; no live keys | Dashboard test sends one small inference request and may be billable; catalog calls are distinct from inference tests. No real-provider result in this workspace. |
| Capability metadata | Partial | Context window, chat, and operator-declared tool support are stored. Tool routing is blocked until the synthetic tool-call eval passes for the current provider/model identity. Modality, streaming, structured-output, provider quota, and task-specific benchmark capabilities are not yet modeled. Tool support is not inferred from model names/catalog text. |
| Manual/adaptive routing | Implemented; deterministic orchestration tests | Manual ordered profile selection; adaptive fast route prioritizes observed latency, while Balanced uses primary and a bounded configured fallback. Routing is capability/status/performance-aware, not a task-specific quality classifier: complexity, risk, urgency, modality needs, and task-category benchmark matching are not automatically scored. Tool routing requires declared `tools` capability. |
| Fast/Balanced/Fusion/Maximum modes | Implemented; fake-provider tests | Balanced default. Fusion: parallel analyses + targeted conflict review + synthesis. Maximum adds critique/revision, at most 7 calls. All report actual model roles, failures, requests, token totals, costs/uncertainty, and degradation. No majority vote or external verification in fusion. |
| Resource/cost bounds | Implemented; deterministic unit tests | Request/minute and per-run request budgets, parallelism, output tokens, context, timeout, fallback, task limits, and fusion estimate ceiling. Dollar ceiling is enforced only with all participant rates configured; estimates are not invoices. |
| Usage and cost reporting | Implemented | Provider-reported token usage and operator-rate estimates; usage/cost are marked incomplete or unknown when provider token data or configured rates are missing. Missing usage is not reported as verified zero. Provider-specific modifiers/cache/tool billing may differ. Latest usage aggregates are bounded. |
| Versioned model evaluation | Implemented; fake response tests | `nova-eval-v1`: marker, JSON, and synthetic tool-call schema (never executes). Passing tool-call schema is required before production tool routing; history can be compared. Not a truth/safety/general-quality benchmark. |
| User outcome feedback | Implemented; API/storage tests | Optional 1–5 rating stored with run metadata. No automated training or automatic routing change from ratings yet. |
| Controlled system self-improvement | Partial foundation; code-change lifecycle not implemented | Metrics/evaluation/feedback are present. No model-weight learning, private-chat training, candidate-code execution, production code patching, high-impact code approval workflow, or automatic rollback. Such changes remain operator-reviewed deployments. |
| Autonomy levels and central policy | Implemented; policy and API tested | A Assisted, B Routine (default), C Advanced, D High; C/D do not exceed installed capabilities. Per-tool allow/approve/deny, explicit-deny precedence, and workspace-relative overwrite scopes. Unclassified tools require approval; existing path validation, backups, and handler gates remain authoritative. |
| Task planner and execution loop | Implemented; unit/API tested with fake provider | Plan → registered tools → actual outcome; modes flow through analysis calls. Level A automatically requires plan review; each tool action is gated centrally. Tool turns use a single capability-aware model; task permission boundary is unchanged. |
| User-configured goals | Implemented; API/database tested | Goals are paused by default; user can explicitly enable hourly/daily/weekly schedules or run a goal manually. Only enabled saved goals are scheduled. Each run creates a SQLite task/checkpoint with goal provenance; scheduled tasks use Balanced mode and existing approvals/budgets. |
| In-process scheduler | Implemented; durable goal/task records, not an always-on service | SQLite-backed due times, atomic dispatch, one run per goal per due window, no catch-up burst, configurable daily cap (default 5). Scheduler is process-local; hosting sleep/restarts pause work. Multiple replicas/process coordination and guaranteed execution are not provided. |
| Bootstrap diagnostics | Implemented; API-tested | Read-only storage/workspace/provider/tool/autonomy/scheduler/auth checks; returns counts/status only, no credential values. Does not configure accounts or run inference. |
| Autonomy policy benchmark | Implemented; deterministic sandbox test | Seven local policy/scheduler cases, executed in a temporary workspace/SQLite database; zero provider/external requests. Not an AI reasoning, truth, or live deployment benchmark. |
| Task states and controls | Implemented and API-tested | Queue/planning/running/waiting approval/paused/completed/failed/cancelled; pause/resume/cancel/emergency stop and checkpoint recovery. |
| Verification | Implemented; tested with fake provider | Separate model-based evidence check when tool evidence and request budget exist. No tool evidence means explicitly unverified. It is not a formal proof. |
| Safe calculator | Implemented/tested | Arithmetic AST evaluator; no `eval`, variables, code execution, or arbitrary functions. |
| Workspace files | Implemented/tested | List/read/search/create UTF-8 text in the selected workspace; traversal/symlinks and common credential/private-key paths rejected; bounded size; existing-file approval and retained backup. No delete, binary/Office parsing, or upload UI. |
| Web research | Implemented behind optional Tavily credential; live use untested | Public search only; no website login, CAPTCHA/paywall bypass, or browser automation. Results are untrusted. |
| Conversation/task/evaluation/goal history | Implemented | SQLite persistence includes prompts/outputs, task checkpoints, goal definitions/schedules, run provenance, profile metadata, evaluation results, and optional feedback. Durability depends on host storage volume. No long-term personal memory or graph. |
| Authentication | Implemented/API-tested | Optional single-user token, HttpOnly SameSite cookie, in-memory sessions that are revoked server-side on logout (a captured cookie stops working immediately), pruned on expiry, and capped so repeated logins cannot grow the store. Hugging Face startup fails closed without a token. No multi-user identity/shared session store; run one worker because sessions are process-local. |
| Low-resource deployment | Implemented/configured; live Space not verified | Docker/HF port 7860; one task worker by default. No GPU/local model required. Hosting persistence, quotas, and sleep behavior depend on owner configuration/provider policy. |
| Engineering quality gates | Implemented; runs in CI | Ruff (configured in `pyproject.toml`, correctness-first rule set), byte-compilation, `node --check` for the frontend, the full pytest suite across Python 3.11–3.13, a Qt job that installs system graphics libraries so the native window test runs instead of skipping, and a packaging job that builds the `.deb` and asserts its version matches `pyproject.toml`/`nova.__version__`. `tests/test_regressions.py` pins previously fixed defects. CI does not verify live provider access, billing, or installation on a target Kali host. |
| Epistemic tracking and provenance | Implemented; unit-tested offline | `nova/cognition/epistemic.py`: claims carry a kind (observation/inference/assumption/prediction/unknown) and a provenance (user, tool_result, external_source, test, memory, model_generated). A statement declared as an observation without observational provenance and an evidence ref is **demoted**, not accepted, so model text can never enter the world model as a measured fact. Confidence is only carried by inference/assumption/prediction. |
| Confidence calibration (§83) | Implemented; needs ~10 outcomes before it reports | Expected calibration error over 5 buckets, Brier score, mean confidence, observed success rate, overconfidence, and a status of well/acceptably/poorly calibrated. Below 10 resolved outcomes it reports `insufficient_data` and publishes no score rather than a flattering one. The engine records a calibration entry only for tasks that actually made a pre-flight prediction; no confidence is invented to fill the ledger. `GET /api/cognition/calibration`. |
| Internal world model (§73) | Implemented; not causal inference | Observations keyed by (subject, predicate) with per-predicate TTLs (`service.state` 30 s, `resource.usage` 15 s, `command.exit_code` never stale), bounded history and LRU eviction (floor 50). Predictions are registered before an action and resolved against the observed result; each contradiction is recorded individually and flags its subject for re-inspection. Hypotheses need 3 confirmations to be `supported` and any refutation is terminal. The engine predicts every tool call's outcome class and resolves it, comparing in a normalized space because tools report their own status vocabulary. No do-calculus, no intervention reasoning, no learned causal graph. |
| Pre-flight meta-reasoning (§72) | Implemented; advisory, never self-authorizing | Before execution the engine derives: understood facts, unknowns, missing evidence, riskiest assumptions, failure modes, capability gaps split into **blocking** (outbound communication, payment, GUI automation, screen capture, system power, account authentication, browser automation, an unregistered tool) versus **policy-gated** (package installation, destructive removal), derived acceptance criteria, the cheapest sufficient verification, abandon conditions, cost estimates, and a rule-based confidence in 0.05–0.9. Persisted per task, emitted as a `cognition` event, and injected into the execution prompt. A `blocked` verdict is reported and surfaced but does **not** cancel a user-authorized task: a model-derived assessment may not override the operator (§84). |
| Post-hoc attribution (§72) | Implemented; evidence-driven, eight causes | Every terminal state — including success — is attributed to `success`, `incorrect_information`, `poor_planning`, `unavailable_tool`, `execution_error`, `bad_success_criterion`, `budget_exhausted`, `cancelled`, or `unknown`, using recorded tool statuses, budget consumption, contradiction counts and criterion totals rather than narrative. `unknown` is returned when the evidence cannot distinguish the causes. A lesson from one run is `tentative`; an unfinished or paused task receives no attribution at all. |
| Counterfactual planning (§74) | Implemented; scores caller-supplied estimates | Options are scored on cost relative to budget, risk banded against the operator-selected tolerance, reversibility, verifiability and authorization friction. Options needing a missing capability, lacking granted authorization, or exceeding budget score 0 and can never be selected. When exactly one option is cheap, low-risk, reversible and verifiable the comparison **short-circuits** and says so, rather than spending requests ranking an obvious answer. `predicted_outcome` is prefixed `Predicted (not yet executed)` and `record_actual` stores the real result separately, giving a measurable forecast-versus-actual rate that excludes unresolved decisions. `POST/GET /api/cognition/decisions`. Not a simulation: nothing is rolled forward, and the weighting is fixed over estimates the caller supplies. |
| Bounded curiosity (§75) | Implemented as planning; rungs are not auto-executed | A seven-rung ladder in cost order — recall from memory, local documentation, external search, specialist model, bounded experiment, write a test case, ask the user — skipping any rung that lacks a tool, lacks authorization, exceeds budget, or falls outside the authorized roots. `within_scope` normalizes paths (collapsing `..`, expanding `~`) and compares resolved absolute paths, so `workspace/../../etc/passwd` is refused; privacy-sensitive gaps refuse local exploration outright. An exhausted budget escalates to the user instead of digging further, and `ExplorationLog` records what curiosity cost. `POST /api/cognition/gaps`. |
| Procedures, transfer and continual learning (§71, §77) | Implemented; lexical retrieval, marker-based transfer | Learned workflows carry steps, preconditions, environment markers, required tools, evidence refs, source task IDs, a version and lineage. Promotion to `established` requires 3 attempts, 2 successes and a ≥60% ratio — **a single success only ever creates a candidate**; an established procedure that drops below 60% is demoted with a recorded reason. `transfer_check` compares environment markers and returns compatible / partially_compatible / incompatible / **unknown** (with confidence 0.0 when nothing is comparable, never a default "compatible"), plus required adaptations and a re-verify list. `correct` and `remove` record reason and provenance, and every mutation is logged. `prune_unreliable` removes only non-established procedures, so accumulating experience cannot erase what works. A new task matching an existing procedure at ≥0.60 reinforces it instead of creating a near-duplicate. A completed run whose independent verification found no evidence is recorded as `not_scored` — neither success nor failure. No weight update of any kind; retrieval is token overlap, so differently-worded procedures will not be found. |
| Multi-agent coordination (§85) | Implemented as planning; not yet driving execution | Roles are **derived from the objective** — each carries a function, the objective feature that produced it, and an output contract — and reuse the identifiers the existing orchestrator already emits (`independent_analysis`, `conflict_review`, `synthesis`, `targeted_critique`, `revision`) rather than inventing persona names. A contested objective gets an extra independent pass; fewer than 4 remaining requests reduces coordination instead of overspending. Subtasks that no registered tool could verify are routed to `clarification` rather than answered from model text. Contradiction detection compares negation markers and numeric tokens over shared subject vocabulary, so semantically-conflicting statements that share no words are not caught. `derive_roles` output is not yet consumed by the fusion pipeline; the existing path is unchanged. |
| Evidence gating of model agreement (§83) | Implemented; deterministic | `reconcile` treats agreement between models as a signal, never as proof: unanimous outputs with no independent evidence ref yield `unverified_consensus` with confidence capped at 0.35 and an explicit warning. One tool result upgrades the same consensus to `confirmed`. Failed participants are listed rather than silently dropped, and evidence that exists but with too few surviving analyses is downgraded from `confirmed`. |
| General intelligence evaluation suite (§86, §89) | Implemented; 30 cases, not a measure of general intelligence | `nova-gie-v1`: 30 executable cases over 11 capability areas, 27 default and 3 held out, each returning passed/failed/skipped/blocked with a recorded measurement. Runs in ~10 ms with zero provider calls and is deterministic, so it can gate CI (`python -m nova.cognition`, exit 1 on any failure or regression). Baselines are versioned in `intelligence_eval_runs`; held-out runs are stored but never selected as a baseline and the CLI refuses to save one from a held-out run. A baseline from a different suite version, or one that stored no per-case rows, is reported as **not comparable** rather than yielding a vacuous "no regressions". Missing tools and configuration limits are reported as `skipped` with the reason named, never as passes. Every report carries `claim_limitations`. `GET/POST /api/cognition/evaluation/*`. |
| Safe self-improvement boundary (§87) | Deliberately minimal; no apply path exists | Evaluation, versioned baselines, regression detection, and correction/supersession/removal of stored knowledge. A learned procedure can influence retrieval ranking only. There is no mechanism by which an AI-generated change reaches code, configuration, permissions, authentication, secret handling, auditing, or shutdown behaviour; no self-modification, auto-promotion into a tool, automatic threshold tuning, or self-granted authority. The security modules are not imported by the cognition layer, and the suite's success criteria are fixed in code. No rollback path is needed because nothing is auto-applied. |
| Cognition failure isolation (§88) | Implemented; tested by injecting a broken layer | Every public `CognitionService` method runs inside a guard and every engine call site is wrapped, so a cognition defect is counted, logged once and reported through `snapshot()["degraded"]` and `GET /api/health` while the user's task still completes. Verified by a test whose cognition layer raises on every method. Existing pause/resume/cancel/emergency-stop/approval controls are unchanged and still take effect immediately. |
| Skill acquisition (§76), multimodal (§79), scientific mode (§80), creative/strategic (§81), social/collaborative (§82) | **Not implemented** | Intentionally absent rather than simulated. §76 is blocked on the reviewed isolation design already tracked as ROADMAP item 13. §79–§82 each need a capability NOVA does not have (perception, experiment execution, generative search, user modelling); where a task needs one, pre-flight reports it as a blocking capability gap. No plugin loader, download-and-execute path, image/audio/screen parsing, experiment runner, citation handling, novelty scoring, or user modelling exists. |
| Cognition user interface | APIs only; no native desktop panel | Sixteen `/api/cognition/*` routes behind the existing access-token gate, with clamped limits and a fixed provenance vocabulary enforced by validation (unknown provenance is a 422). The PySide6 desktop window does not render cognition state, and the browser UI has no cognition panel yet. |
| Event-driven intelligence bus (§91) | Implemented; in-process | `nova/events.py`: `nova-event-v1` schema, wildcard patterns, causal-chain cycle & depth-4 refusal, dedupe window, subscriber idempotency keys, retries, bounded queue, and mandatory `AutonomyPolicy` check before tool-bearing subscribers execute. |
| Plugin manager & Developer SDK (§92, §109) | Implemented; checksum-verified | `nova/plugins.py`: 11-part `PluginManifest`, install-disabled with zero inherited permissions, explicit permission grant on enable, AST boundary blocking `nova.db`/`nova.autonomy` imports, sandboxed subprocess execution, candidate staging workflow, and 4 built-in SDK examples. Cryptographic GPG/Minisign signing not yet wired. |
| MCP client & integration gateway (§93, §105) | Implemented; optional interop | `nova/mcp_client.py`: JSON-RPC 2.0 over `stdio`, `https`, and `memory`; tool/resource discovery; input schema validation; never forwards conversation history or local files; tags outputs `untrusted_external`; credential revocation; gateway enforces minimum per-operation scopes (`auth_verified` never grants blanket access) and rate limits. |
| Knowledge engine & hybrid search (§94) | Implemented; FTS5 baseline + optional embeddings | `nova/knowledge.py`: SQLite FTS5 (`porter unicode61`) with BM25, snippets, line/page citations, provenance, 30-day staleness flags, code symbol search, incremental hash check, deleted-file removal, forget API, and RRF fusion when an embedder is configured. Binary PDF/Office files are refused rather than garbled. |
| Context & memory optimization (§95) | Implemented; local extractive | `nova/context_manager.py`: 5 separated compartments (`confidential_credentials` excluded from prompts), protected anchors (objective, constraints, permissions, blockers, error evidence), `verified_facts` vs `hypotheses` split, extractive stage summaries, fingerprint deduplication, and `requires_source_recheck` on high-impact actions. |
| Terminal workspace (§96) | Implemented; process-local sessions | `nova/terminal.py`: multi-session workspace, named workdirs, live stdout/stderr callbacks, `nova` vs `user` actor attribution, `pty` interactive support, process-group cancellation, templates, diff inspection, redacted diagnostic export, and side-effect replay guard. |
| Workflow DAG & cross-app automation (§97, §98) | Backend implemented; Qt canvas deferred | `nova/workflows.py`: 14 block types, cycle/orphan/cost/schedule validation, runtime + save-time policy check, JSON import/export, natural-language draft proposal, dry-run mode, and checkpointed 8-stage notes→report→checklist→email-draft flow preserving verified stages on partial failure. |
| Safe execution sandbox (§101) | Implemented; fail-closed | `nova/sandbox.py` + `nova/sandbox_child.py`: probes `bwrap`, configured `podman`, then `unshare` user+mount+pid+ipc+uts+net namespaces; read-only `/`, scoped writable binds, hidden credential paths, `RLIMIT_*`, `PR_SET_NO_NEW_PRIVS`, `SIGKILL` timeout escalation; `process_only` explicitly marked NOT a sandbox; refuses risky execution when isolation is unavailable. |
| Developer & data workspaces (§100, §108) | Implemented; pure-Python baseline | `nova/devtools.py` (git status/diff, destructive-git/protected-branch/deploy approval gate, repo/symbol search, dependency checks, `.venv`-first inspection, traceback parser, sandboxed candidate-patch runner) and `nova/data_workspace.py` (streaming CSV/TSV/JSON/JSONL/log/Markdown profiler, filter/group, chart spec, document diff, citations, reproducible Python script). |
| Visual & voice modalities (§99, §107) | Modular core; hardware capture optional | `nova/modalities.py`: opt-in screenshot/OCR wrappers (`CONTINUOUS_SCREEN_CAPTURE=False`), pure-Python image diff, `visual_observation` tagging (`verified_system_fact=False`), pluggable local-first STT/TTS with push-to-talk, barge-in, mic indicator, typed fallback, identical planner/policy routing, and `SPEAKER_ID_AUTHORIZES_PRIVILEGED=False`. |
| Observability, privacy, health, updates & resources (§102–§104, §106, §110–§113) | Implemented; local-by-default | `nova/observability.py` (redacted W3C/OTel spans, `explain_task`), `nova/governance.py` (9-category privacy inventory, transmission gate, 15-indicator health center & redacted diagnostic bundle), `nova/updates.py` (trusted manifest, SHA-256, SQLite backup/rollback, offline queue revalidation), `nova/resources.py` (dual-core ~10 GB adaptation), and `nova/capabilities.py` (24 probed features). |
| Email/calendar/GitHub/cloud storage | Planned | No connector is active. |

No agent browser tool, background host-control companion, arbitrary model shell string, or unsandboxed candidate-code workflow is implemented. |
| Voice/multimodal/document upload/durable worker | Planned/not implemented | No voice, microphone, image/PDF/Office extraction, external durable worker, guaranteed always-on schedule, or quiet-hours manager. The current scheduler is in-process only. |
